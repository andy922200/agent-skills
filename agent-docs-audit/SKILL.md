# agent-docs-audit

## 何時使用

- 決定專案需要哪些代理文件、各自放什麼。
- 稽核既有文件是否與實際程式、資料、指令一致，並整理重複與寫法。
- 精簡 `AGENTS.md`，把不該放的內容移走。

## 分層與取捨

- 檔名只有 `AGENTS.md` 由工具綁定。Claude Code 讀 `CLAUDE.md`，可在其中以 `@AGENTS.md` 匯入。
- `init.sh`、progress、`feature_list.json` 與專案文件的檔名都可自訂，沒有工具會自動載入或執行它們。`AGENTS.md` 必須寫出實際檔名與用途，代理是照文字找檔案。
- 不確定某個工具是否自動載入某檔案時，不寫死該行為，改為在 `AGENTS.md` 明確指示。
- 新增任何檔案前先問三件事，答不出就先不加：
  1. 這份資訊在別處已有正本嗎？
  2. 誰負責更新？沒人更新就會過期。
  3. 沒有它，代理具體會在哪一步出錯？
- 分級：
  - 小專案：只要 `AGENTS.md` 加驗證指令。
  - 一般長期專案：再加 `init.sh`，僅在環境難以手動準備時。
  - 長時間或多代理接力：才需要 progress 與 `feature_list.json`。
- 過期的狀態檔比沒有更糟，代理會相信它。歷史已在 git log、evidence 或 changelog 時，不要另建第二份。
- `AGENTS.md` 只放穩定規則：專案概述、文件指路、開工順序、完成前驗證、禁止事項。品牌、市場、筆數等會變動的清單與進度不放在這裡。
- `feature_list.json` 的語意是驗收項目與通過狀態，不是工具清單。工具與權限屬各家代理自己的設定，不要試圖統一。

## 稽核流程

1. 完整讀過目標文件，列出可核對的主張：路徑、數字、路由、指令、欄位名、版本規則。
2. 唯讀對照實際來源：`ls`、`grep`、讀程式，或用腳本計數。不憑目錄或檔名推斷職責，寫功能說明前先讀對應程式。
3. 分類問題：
   - 事實錯誤：與程式或資料不符。
   - 重複維護：同一份資料在多份文件各寫一次。
   - 讀者錯置：AI 專用指令放在人類文件，或反之。
   - 寫法：超長條目、章節名稱誤導、同一規則寫兩次。
4. 去重時指定單一正本，其餘改為指向，並保留無法從別處推得的內容。選哪一份當正本、AI 指令要不要移走，是使用者的決定，用提問確認。
5. 資料層或契約層的不一致（例如命名大小寫）：先回報影響與建議，取得同意再修改。已提交的不可變更紀錄與 Schema 不得順手更動。
6. 驗證：grep 確認舊數字與舊路徑已清除、相對連結的檔案都存在、文件裡寫的指令實際執行過。

## 交付回報

- 依「事實錯誤、去重、寫法、待使用者決定」分類列出。
- 註明哪些已驗證、哪些沒有跑，不把未執行的檢查說成通過。

## 與其他 skill 的關係

- commit 訊息與提交由 `git-commit-msg` 處理。
- 要讓各 commit 能獨立 cherry-pick：互相依賴的引用改動，與被引用的檔案放在同一個 commit。
